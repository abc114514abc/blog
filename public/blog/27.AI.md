# AI效率提升

> 用 AI 写代码，感觉怎么都用不出别人那种"又快又好"的效果？问题通常不在模型，而在你怎么喂它、约束它、验收它。

## 一、先转变观念：AI 是"执行力极强的实习生"，不是"全能大脑"

用 AI 效率低的人，多数是把**思考外包给了模型**。正确顺序永远是：

> 自己先想清楚（伪代码 / 数据结构 / 流程） → 把你的思考 + 约束 + 上下文喂给 AI → 让它实现细节、补测试、查边界。

你的核心能力从"写代码"变成三件事：**定义意图 → 控制生成 → 验证产物**。

## 二、先认识敌人：AI 幻觉

**什么是幻觉**：模型输出非常流畅、语气非常自信，但内容是编造的、错的，或根本不存在的。它不是一个"坏模型"，而是它的本质决定的——它是**预测下一个词的统计模型**，追求的是"听起来合理"，而不是"事实正确"。

在代码场景里尤其危险：语法是对的、结构是完整的、一眼看过去没毛病——但可能调用了不存在的函数、用了过时的 API、或者逻辑和你的业务规则对不上。**它不会主动告诉你"我不知道"。**

### 为什么会幻觉

1. **知识截止**：训练数据有时间边界，新框架、新 API 它不知道，但会"猜"一个看起来合理的。
2. **无法"运行"代码**：只能推断，不能编译、不能执行，很多错误它自己看不见。
3. **意图不明确**：输入越模糊，它需要"脑补"的越多，幻觉概率越大。
4. **训练数据噪音**：网上本身就有大量错误、过时的代码，被它当成"正确答案"吸收了。

### 代码生成中的三类幻觉

1. **资源虚构**：编造不存在的工具类、方法、依赖。比如让它用"项目自带的加密工具类"，它编一个 `EncryptUtils.encrypt()`，项目里根本没有。
2. **版本适配**：无视框架版本，写过时或超前的语法。你在用 SpringBoot 2.x，它给你写 3.x 才有的 API。
3. **业务逻辑**：忽略既有业务规则。系统规定"密码错误返回 400"，它默认给你返回 500。

### 怎么识别

- **没见过的东西先查**：它提到的类、依赖，先 grep 项目里有没有。
- **看它敢不敢承认不确定**：真懂的 API 直接给；用"通常""一般""可以试试"这种模糊词的，警惕。
- **运行看结果**：编译一遍、跑个测试，比盯着代码看有效得多。
- **让它解释"为什么对"**：理由含糊，很可能在编。

## 三、提示词模板：像写技术规格说明书一样提问

80% 的问题出在输入，不在模型。一个高质量 Prompt 应该覆盖：角色、任务、技术栈、输入输出、约束、边界、验收——

```text
【角色】你是 10 年经验的后端工程师，追求可读性和性能
【任务】实现用户改密码接口
【技术栈】JDK 17 + SpringBoot 3.2 + MyBatis-Plus，禁止编造未声明的工具类
【输入/输出】入参 JSON 结构是 X；返回 { code, message, data }
【约束】密码用项目自带的 BCrypt 工具类；密码错误返回 400 而非 500
【边界】空值、token 过期、并发重复提交如何处理
【验收】单测必须全过；单接口 P99 < 80ms
```

## 四、约束的艺术：防幻觉的核心手段

1. **环境全量绑定**：语言版本 + 框架版本 + 依赖清单 + 编码规范，一次性说死。
   - 反面："写个用户改密码接口"（AI 会乱编）
   - 正面："JDK17 + SpringBoot3.2 + 项目自带 BCrypt 类，禁止引入新依赖"
2. **负面约束**：明确禁止什么——"不用弃用库""禁 O(n²)""禁止循环里阻塞 IO"。
3. **反向提示**："信息不足必须提问，不允许自行假设"——最治"看似合理、实际不可用"。
4. **验收标准当死亡红线**：列出"全部满足才合格，否则重写"的硬条件。

对应关系：**环境全量绑定 → 治版本幻觉；禁止编造、禁新依赖 → 治资源虚构；验收 + 测试闭环 → 治业务逻辑幻觉；反向提示 → 从源头堵住脑补空间**。

## 五、工作流：迭代比一次性更重要

- **一次只做一件事**：复杂需求拆成 分析 → 方案 → 代码 → 修复，四步分开，别一步到位。
- **计划先行**：改动超过 2-3 个文件，先让它列计划，你确认后再动手。
- **迭代而非一击命中**：生成 → 验证 → 反馈，每轮只补一个维度。
- **少样本示例**：给一对"输入→输出"例子，比十句描述都管用。
- **验收闭环**："改完跑一遍测试套件，确认没破坏别的"。

## 六、项目级沉淀：写一个 CLAUDE.md

把反复说的规范写进项目根目录的 `CLAUDE.md`（测试命令、命名风格、架构约定、禁用项），之后每次会话 AI 自动加载，不用重复交代。

## 七、日常习惯

- 让 AI 先**读相关文件再动手**，别空手乱猜。
- 改代码后**读 diff 复核**，安全/敏感改动别全信。
- 无关任务开新会话，长会话做上下文压缩，避免污染。
- 给可量化的完成标准："把 bundle 压到 200KB 以下""测试全绿"。

---

**一句话总结**：把 AI 当"执行力极强的工程师"，你自己当架构师 + 测试负责人，用**结构化输入 + 硬约束 + 小步迭代**代替"一次说一大段让它全包"。

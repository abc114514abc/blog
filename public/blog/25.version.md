# 版本号命名学习
版本号是软件、产品或接口在更新和迭代过程中用来标识特定状态的唯一标记。系统地理解版本号，主要可以从**语义化规范**、**发布阶段标识**、**依赖匹配规则**以及**变体策略**四个核心维度来掌握。

---

## 1. 语义化版本控制（Semantic Versioning / SemVer）

这是目前现代软件开发中最通用、标准的版本控制规范。标准格式为：

`主版本号.次版本号.修订号 (MAJOR.MINOR.PATCH)`

例如：`v2.4.1`

- **主版本号（MAJOR）**：做了**不向下兼容**的 API 修改或破坏性更新（Breaking Changes），调用方可能需要修改代码才能升级。
- **次版本号（MINOR）**：增加了**向下兼容**的新功能/新特性（Feature），旧代码无需修改即可运行。
- **修订号（PATCH）**：做了**向下兼容**的问题修复（Bug Fixes）或性能优化，不涉及任何逻辑接口的变更。

---

## 2. 阶段性标记与预发布标识

在发布正式稳定版（GA, Generally Available）之前，通常会在版本号末尾加上**连字符（`-`）**和阶段标识：

| 标识阶段 | 全称 / 名称 | 含义与使用场景 |
| :--- | :--- | :--- |
| **Alpha** | Internal Test | 内测版。功能仍在开发中，可能存在较多 Bug，仅供团队内部测试。 |
| **Beta** | Public Test | 公测版。功能基本冻结，开放给部分早期用户或社区，用以收集反馈并捕获边界问题。 |
| **RC** | Release Candidate | 候选发布版。代码已高度稳定，若测试未发现重大严重缺陷，将直接作为正式版发布。 |
| **Snapshot**| 快照版 | Maven/Java 体系常用。表示该版本处于持续开发中，每次 build 都会更新依赖。 |
| **Release / GA** | Official Release | 正式发布版。推荐全量覆盖所有生产环境用户的最终稳定版本。 |

> **流转示例**：`1.0.0-alpha.1` → `1.0.0-beta.2` → `1.0.0-rc.1` → `1.0.0`



## 3. 依赖范围标识符（常见于 npm / Cargo 等包管理器）

在项目的依赖配置文件（如 `package.json`）中，通常使用以下符号来指定可接收的版本范围：

- **精确匹配（`1.2.3`）**：严格锁定使用 `1.2.3`，不允许自动更新。
- **波浪号（`~1.2.3`）**：允许自动升级 **PATCH** 版本（允许升级到 `1.2.x`，但不升级到 `1.3.0`）。
- **插入符号（`^1.2.3`）**：允许自动升级 **MINOR** 和 **PATCH** 版本（允许升级到 `1.x.x`，但不出 `2.0.0`）。
- **通配符（`*` 或 `x`）**：接受任意版本（风险极高，生产环境严禁使用）。

### ⚠️ 0.x.x 版本的特殊边界（非常重要）
在 SemVer 中，`0.y.z` 表示**早期开发阶段**，API 随时可能发生破坏性变更。
- `^0.2.3` 含义等同于 `~0.2.3`：它**只会更新 PATCH**（`0.2.x`），**不会**自动升级到 `0.3.0`。
- `^0.0.3` 只会匹配 `0.0.3` 本身，**不会**升级任何数字。

## 4. 常见的版本策略变体

除了 SemVer，在不同的产品形态中还会使用以下版本命名模式：

1. **日历版本控制（CalVer, Calendar Versioning）**
   - **格式**：`YY.MM.MICRO`（例如 Ubuntu 的 `22.04`、`24.04`，或 Python Pip 的 `23.0`）。
   - **适用场景**：定期频繁发布、业务受时间驱动的项目。
2. **构建流水线版本（Build Number / Git Commit Hash）**
   - **格式**：`1.2.0+20260726` 或 `1.2.0-sha.a1b2c3d`
   - **适用场景**：CI/CD 持续集成部署追踪，移动端 App（App Store/Google Play 要求构建号严格递增）。

---

## 5. 工程落地的最佳实践

1. **零版本起步**：新项目建议从 `0.1.0` 开始迭代；一旦对外公开发布并具有稳定性承诺，升至 `1.0.0`。
2. **破坏性变更必升 MAJOR**：即便只删除了一个极其边缘的接口，只要影响了向下兼容性，就必须升主版本号。
3. **锁定依赖版本文件**：在生产项目中提交 `package-lock.json`、`yarn.lock` 或 `Cargo.lock`，确保协同开发和 CI 环境中的版本一致性。

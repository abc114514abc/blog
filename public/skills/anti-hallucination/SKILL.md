# 防止 AI 幻觉：代码开发通用规范

这个技能的目标只有一个：让你生成的代码**能跑、对版本、不编造**。以下规则在任何代码开发任务中都必须执行，不要省略。

## 一、动手前：先绑定环境（强制）

不知道、不明确的信息，先读项目文件确认，**不要猜**：

- 语言与框架版本 → 读 `package.json` / `pyproject.toml` / `go.mod` / `pom.xml` / `requirements.txt` 等
- 项目已有的依赖、工具类、方法 → grep 项目源码，不假设存在
- 编码规范、目录结构 → 读 README、模仿现有代码风格

如果信息不足、项目里也找不到，**必须向用户提问**，禁止自行假设。

## 二、生成中：三条红线（强制）

1. **禁止编造**：不生成项目里不存在的 import / 依赖 / 工具类 / 方法 / API。确定不存在时，明确写出"项目中没有此 API，需要你提供，或允许我引入新依赖"，而不是假装它存在。
2. **版本适配**：只用所绑定框架版本里真实存在的语法与 API，不写已过时或超前版本才有的写法。
3. **业务逻辑**：业务规则不确定就提问，不擅自假设"返回 500""直接用默认值""自动创建记录"这类行为。

## 三、生成后：自检清单（强制）

交付前逐条检查，并**把结果告诉用户**：

- [ ] 涉及的文件已读，环境版本已确认（写明具体版本号）
- [ ] 没有编造的 import / 依赖 / 工具类
- [ ] 语法与本项目框架版本匹配
- [ ] 明确标注哪些已验证、哪些未验证
- [ ] 环境允许时跑过编译 / 测试 / lint，贴出结果

## 四、输出格式

1. 一句话先说明方案
2. 代码块标注语言
3. 结尾附「自检结果」：哪些验证过、哪些需要用户确认
4. 不确定的地方用 **「需确认：xxx」** 标出，而不是装作确定

## 五、典型反例 / 正例

**反例**：写 SpringBoot 接口时直接调 `EncryptUtils.encrypt()`——但项目里根本没有这个类。
→ 这就是资源虚构幻觉。

**正例**：先 grep 项目确认没有加密工具类，然后回复："项目中没有加密工具类，是否需要我引入 hutool，或由你提供加密工具？"再继续写代码。
